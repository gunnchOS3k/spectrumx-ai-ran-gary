# Why more switching can produce a worse result

A computer service can run locally, on a nearby server or in a remote cloud. A controller chooses where work runs and which connection it uses. This paper asks whether a preserved controller described as digital-twin informed actually improves the score in its own synthetic experiment after switching costs and baseline behavior are examined.

## What the researchers did

Two historical software versions were kept separate and reproduced. Each held-out study uses five seeded sets of 24 episodes, with 16 slots per episode. The research unit is a seed average, not an individual user or packet. Network conditions, energy budgets and delays are generated from authored formulas. There is no measured radio channel, physical edge server, battery discharge or operator deployment in this evidence.

In the original study the procedural twin policy scores about 0.01360 units worse than the cloud-fallback comparison policy. Every held-out seed favors that comparison. A separately reproduced revised version also retains an unfavorable twin result. These negative results are preserved because they answer the actual hypothesis. A simpler fixed linear selector does better, but it does not establish that digital-twin information caused the difference: controllers use different features and different computational work.

## A worked example

Imagine two artificial time slots. Keeping one action produces a gross score of .90 in each, averaging .90. A switching policy produces .94 in each, but its second action changes both network and processing location. The configured charge is .05+.03=.08, so its net scores are .94 and .86, again averaging .90. More gross benefit can disappear after transition charges. These values illustrate arithmetic; they are not newly collected observations or measured seconds of handover.

The actual archived study has the same kind of tradeoff. A small gross improvement is outweighed by added configured switching deductions. A retrospective graph changes the charge on fixed actions to explain this result. It does not rerun the controller at each price or prove a safe threshold in real systems.

## Why names deserve inspection

A baseline named no_adaptation still changes network when terrestrial access is unavailable. A static baseline can retain an unavailable action and still receive a score because feasibility is not fully enforced. An oracle is only a greedy evaluator of a restricted current action set, rather than a guaranteed optimum across the whole episode. An interval overlapping zero against it is inconclusive, not proof that two policies are equivalent.

A good comparison requires fair opportunities: the same permitted observations, a feasible action set, a comparable compute budget, honest costs and an outcome representing an actual task. The present code does not establish all those properties. Its energy and delay values are proxies, and its service-quality fidelity action is different from whether a digital twin accurately predicts the physical world.

## Explore the idea

Use a paper-and-pencil trace with three slots. Mark a connection choice and processing location for each. Count changes after the first slot, then compute a gross score and subtract declared transition charges. Repeat with a controller that stays put. Explain when a switch helps and when its charge exceeds the gain. Label every quantity as an invented example. Do not use this score to make a purchase, emergency or network-control decision.
